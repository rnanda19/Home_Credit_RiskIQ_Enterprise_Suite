# Data Privacy & Handling Policy

This document exists to close a real, disclosed gap: the enterprise
production-readiness review of this suite found 0 hits for "GDPR",
"CCPA", or "PII" anywhere in the repository. This is that missing
documentation.

## What data this suite actually uses

Every notebook and service in this repository is built against the
[Home Credit Default Risk](https://www.kaggle.com/competitions/home-credit-default-risk)
Kaggle competition dataset. That dataset is:

- **Already anonymized at the source.** Every record is keyed by
  `SK_ID_CURR`, a synthetic numeric identifier assigned by Home Credit /
  Kaggle for the competition. There are no names, addresses, phone
  numbers, email addresses, national ID numbers, or other directly
  identifying fields anywhere in the dataset.
- **Not redistributed by this repository.** `data/raw/` and
  `data/processed/` are committed as empty directories (`.gitkeep` only,
  per `.gitignore`) — anyone running this suite downloads the real
  dataset directly from Kaggle under Kaggle's own competition terms. This
  repository never stores, serves, or transmits a copy of the underlying
  data.
- **Used for portfolio/demonstration purposes only.** No output of this
  suite is used to make a real lending decision about a real person. The
  FastAPI services in each Mega Project accept synthetic or
  competition-sourced records for demonstration scoring, not live
  applicant data.

## Data classification

| Category | Present in this dataset? |
|---|---|
| Directly identifying PII (name, address, phone, email, government ID) | No |
| Indirect/quasi-identifiers (income, employment type, family status, housing type) | Yes — present in the Kaggle schema, at the anonymized-record level |
| Protected-class demographic fields (race, ethnicity, religion, disability) | No — this is also why no fair-lending/bias audit is possible against this dataset; see the production-readiness gap analysis |
| Financial account numbers, card numbers | No |
| Real-time location data | No |

Even though the direct-identifier risk is already low by construction,
the quasi-identifiers above are still handled under the retention and
access rules below, consistent with how a real deployment would treat
them.

## Retention

- Raw and processed data directories (`data/raw/`, `data/processed/`)
  are `.gitignore`d and never committed to version control. Anyone
  running this suite is responsible for their own local copy and its
  retention, per Kaggle's own dataset terms.
- Trained model artifacts (`decision_engine/artifacts/*.joblib`,
  `decision_engine/reports/*`) are also `.gitignore`d and regenerated by
  re-running the owning notebook — see `MODEL_REGISTRY.md`. They are not
  retained in version control either.
- No service in this suite writes request data to persistent storage
  today. Each `/score` (or equivalent) endpoint is stateless: it accepts
  a record, returns a prediction/segment/reason codes, and does not log
  or persist the input record. (If request logging is added in the
  future for observability — see the production-readiness gap analysis's
  Observability row — that logging must exclude or hash any
  quasi-identifier fields before being written anywhere, to keep this
  guarantee true.)

## Right to erasure

Because this suite does not persist request data or maintain a database
of scored individuals, there is no standing record to erase in the
deployed services themselves. The only retained artifacts are:

1. The Kaggle dataset copy each user downloads locally — erasure means
   deleting that local `data/raw/`/`data/processed/` copy, which is
   already excluded from version control.
2. Trained model bundles — these are statistical artifacts derived from
   the full training set, not a lookup table of individual records; they
   do not contain retrievable per-record data and are regenerated (not
   incrementally updated) each time a notebook is re-run.

If this suite were extended to a real production deployment handling
real applicant data, a right-to-erasure procedure would additionally
need: a request-intake process, a way to locate and delete the specific
applicant's records across any request-logging or feature-store layer
added at that point, and a documented SLA for completing the deletion —
none of which exists yet because none of the underlying storage that
would require it exists yet either.

## Third-party data sharing

This suite shares no data with any third party. All computation happens
locally or in this suite's own containers/services; no external API call
in any service transmits applicant-level data outward.

## Scope and honesty note

This document describes the data-handling posture of a portfolio
project built on an already-anonymized public competition dataset. It is
not a substitute for a real GDPR/CCPA compliance program, which would
require a Data Protection Impact Assessment, a designated data protection
contact, breach-notification procedures, and legal review specific to
whatever real jurisdiction and real personal data a production deployment
would actually touch. Those are out of scope here because there is no
real personal data in this repository to protect them against — this
document exists so that fact is written down and verifiable, not just
assumed.
